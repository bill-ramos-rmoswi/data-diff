This covers the work done in the devcontainer on 10 and 11 November 2026:

| Work | Shipped as |
| --- | --- |
| SAP ASE as source and target | PR #3, v0.13.0 |
| Db2, SQL Server and ASE → PostgreSQL benchmarks | PR #4, closed and redone as commit 3ef5457 |

The figures come from the 7 Claude Code transcripts of those two days, `git log`, and `gh pr list` / `gh run list`. Transcripts from before 10 November 16:33 UTC were lost when the devcontainer was rebuilt, which is what PR #7 fixed, so the Db2 and earlier sessions aren't counted.

One session accounts for 72% of all cache reads. Each turn re-reads the whole context, so cost grows with context size times turn count. A single thread that carries spikes, test output, review and the PR is the most expensive way to work, even when it succeeds.

## What went well

- **The one-shot prompt worked.** [SAP-ASE-One-Shot-Prompt.md](SAP-ASE-One-Shot-Prompt.md) set out measured server facts, the user's answers, ground rules, numbered stop conditions and a definition of done. A new database driver went from start to open PR in about 70 minutes, and merged the same day with every CI job green, the new ASE job included.
- **CLAUDE.md keeps what was learned.** Its "easy to get wrong" sections now hold about 40 measured facts about ASE, Db2 and SQL Server. Later sessions didn't rediscover them.
- **The tools check themselves.** `run_perf.py` fails unless data-diff reports exactly the rows it changed. `seed.py` compares counts, sums and checksums against PostgreSQL. So the published numbers can be trusted.
- **Every pair is tested in CI**, ASE included, and releases come from tags with a wheel attached.
- **The guardrails held.** Auto mode refused to read the git credential token and refused an unrequested `gh pr reopen`.

## What could have gone better

1. **One giant context.** Phases that could have been separate sessions (spike, design, implement, review, ship) ran in one thread, with one subagent in 600 turns. Probe and test output went into the conversation in full.
2. **Spike scripts were rewritten each time.** Each probe was a fresh heredoc with its own pyodbc or FreeTDS connection code. Four failed on ASE limits (16 KB expressions, cp850) that are now in CLAUDE.md. There was no reusable probe tool.
3. **A design covered one dialect.** The large-value plan was rejected with "Would this approach be the same for SQL Server, and for Db2?", because it was designed for ASE first, although hashdiff needs every dialect to agree.
4. **Scope was assumed, not asked.** The benchmark PR covered 4 GB and every pair, but the user wanted 2 GB and on-prem → Aurora PostgreSQL only. It was closed and redone.
5. **Handoff by paste.** Two sessions began with output pasted from the one before. One of them was stopped after it printed a whole file and the environment. No memory carried the next step.
6. **Tool friction cost turns.**
   - `gh run list --commit` doesn't exist in older `gh` versions.
   - `gh pr edit` hits a GraphQL error about Projects (classic). The workaround is `gh api -X PATCH`.
   - Polling with `sleep` is blocked, so waits need a background task or Monitor.
   - `grep` returns a non-zero exit code when nothing matches, which broke `&&` chains.
7. **A release was tagged on a red master.** An external apt mirror outage turned master red after PR #5. The v0.14.0 tag was pushed anyway, and its release run failed until PR #6 fixed CI.
8. **The top model ran checklist work.** Fable ran "what's left to be production ready?", which a smaller model could have done. Only the design and encoding work needed it.

## What changes

### Skills, in `.claude/skills/`

Each skill is short and points to CLAUDE.md rather than copying it.

| Skill | What it does | Fixes |
| --- | --- | --- |
| `/db-probe` | Runs SQL on any configured database with [dev/probe.py](../../dev/probe.py), through data-diff's own drivers. At most 20 rows each, errors on one line, `--repeat` for timing. It lists the documented traps to check first. | 1, 2 |
| `/test` | Picks the smallest suite for a change, runs it in the background with a timeout, and reports only the counts, the `Testing databases:` line and failures. | 1 |
| `/cross-db-design` | Before planning, asks scope questions, then requires a probed behavior table for PostgreSQL, SQL Server, Db2, ASE and MySQL. | 3, 4 |
| `/perf` | Seeds and checks the perf tables, runs `run_perf.py` for the agreed pairs in the background, and compares runs only beyond the 20% noise. | 4 |
| `/ship` | Format, test, commit, PR, CI watch, merge, and tag only on a green master with a matching version. Includes the `gh` pitfalls. | 6, 7 |
| `/ci-triage` | Hands a failed run to a small-model agent and relays a 10-line diagnosis. | 1, 7 |

`/shutting-down` now always writes a `handoff` memory with the next step as a prompt you can paste and the model it needs, and `/hello` reads it back (fixes 5).

### Lower-cost agents, in `.claude/agents/`

| Agent | Model | Use |
| --- | --- | --- |
| `ci-triage` | Haiku | Reads failed CI logs and returns 10 lines. It only reads. |
| `explorer` | Haiku | "Where is X?" lookups, answered with `path:line` |
| `test-runner` | Sonnet | Runs suites and returns the counts and trimmed failures |
| `docs-writer` | Sonnet | Writes README, CLAUDE.md and PR bodies from a diff and the results |

Keep Opus or Fable for dialect design, hash and encoding debugging, and `/code-review high`. Use Sonnet for implementation that follows a settled design, and for running tests and benchmarks. Use Haiku for reading logs and finding code.

### Working in phases

Long tasks run as phases in separate sessions:

1. Spike with `/db-probe`.
2. Design with `/cross-db-design`, in plan mode.
3. Implement.
4. Test with `/test`.
5. Benchmark with `/perf`.
6. Review with `/code-review`.
7. Ship with `/ship`.

`/shutting-down` ends each phase with a `handoff` memory, and `/hello` starts the next. The [Faster-Checksums-One-Shot-Prompt.md](Faster-Checksums-One-Shot-Prompt.md) is the first prompt written this way. It names the skill, agent and model for each phase.
